# SRPG 原型（M0 ~ M1）

一个可运行的战棋（SRPG）骨架：网格渲染、回合制、移动范围、攻击范围、战斗结算、敌方 AI，全部跑在浏览器里。

**核心不是这些功能，而是这套分层：**
纯逻辑（可在 Node 里跑、可单元测试、可批量模拟）× 薄渲染层（换引擎只改一层）。

---

## 快速开始

```bash
pnpm install
pnpm dev          # → http://127.0.0.1:5173
```

其他命令：

```bash
pnpm test         # 跑单元测试（250+ 断言，纯 Node，秒级）
pnpm test:watch   # 监听模式
pnpm smoke        # 浏览器入口冒烟测试：抓"单测全绿但浏览器白屏"那类故障
pnpm typecheck    # 只做类型检查，不产出
pnpm sim          # 所有关卡各跑 300 局，输出汇总表
pnpm sim 1000     # 每关 1000 局（测量更准）
pnpm sim 1000 plain-01   # 只跑指定关卡，输出完整详情（含各兵种存活率）
pnpm sweep        # 参数扫描：一次跑完网格，看平衡对旋钮的响应曲线
pnpm stall        # 僵局诊断：把"打满回合"的对局直接画出来
pnpm campaign     # 战役模拟：从第一关打到最后一关，**带着队伍成长**
pnpm build        # 类型检查 + 打包到 dist/
```

> 遇到"端口占用"就 `pnpm dev --port 5174`。

### ⚠️ 首次安装前必读（两个环境坑）

**1. pnpm 10+ 默认拦截依赖的构建脚本，会让整个工程瘫痪。**

`esbuild` 必须执行 postinstall 放置平台二进制，否则 vite / vitest 启动即失败。
更坑的是：pnpm 会在**每条命令**前跑一次依赖状态前置检查（内部又调 `install`），
所以一旦 `install` 以 `ERR_PNPM_IGNORED_BUILDS` 退出 1，`pnpm test`、`pnpm typecheck`
会连启动都做不到，报错还完全不指向真正的原因。

本仓库已经在 `pnpm-workspace.yaml` 里放行了：

```yaml
allowBuilds:
  esbuild: true
```

注意字段名的变迁：pnpm 10 是 `pnpm.onlyBuiltDependencies`（写在 package.json 里），
**pnpm 11 改成了 `allowBuilds` 映射，写进 `pnpm-workspace.yaml`**，
再放 package.json 里会被静默忽略并打印警告。

**2. 国内直连 GitHub Releases 大概率卡死。**

装 PowerShell 7、Node、或其他从 GitHub Releases 下载的工具时，
直连会长时间停在 0 字节。清华 TUNA 有 GitHub Releases 镜像，速度差两个数量级
（实测 101 MB：GitHub 卡几十分钟无进展 → TUNA 5.2 秒）：

```powershell
# 以 PowerShell 7 为例
$url = 'https://mirrors.tuna.tsinghua.edu.cn/github-release/PowerShell/PowerShell/LatestRelease/PowerShell-7.6.6-win-x64.zip'
```

## 操作

| 输入 | 作用 |
|---|---|
| 左键点我方单位 | 选中 —— 显示蓝色移动范围 + 红色威胁范围 |
| **左键点红格里的敌人** | **攻击**。不需要先移动，原地就能打 |
| 左键点蓝格 | 移动过去（会显示实际路径）；移动后仍可攻击或待机 |
| 左键点**琥珀格** | 移动过去，但**这一格就是终点**（敌方控制区，ZOC） |
| 左键点其他位置 | 移动**前** = 取消选择；移动**后** = 待机 |
| 悬停敌人 | 侧边栏显示战斗预测（**相克关系** / 命中率 / 伤害 / **暴击率** / 是否被反击 / 会不会死） |
| 打一场 | 单位头顶飘 `+N EXP`；攒满 100 就 `LEVEL UP` 并列出涨了哪些属性 |
| 侧边栏单位卡片 | 显示 **Lv**、生命条（红/黄/绿）、**经验条**（蓝色）、**TP 条**（紫色）和携带的武器 / 战技 |
| **Q** | 切换战技（普通攻击 → 各个战技循环），侧边栏的预测会实时跟着变 |
| **数字键 1~9** | 让选中单位装备第 N 把武器（**不消耗行动**，打完也能换） |
| `Tab` | 在携带的武器之间循环 |
| `Space` | 选中单位待机；未选中时结束我方回合 |
| `E` | 结束我方回合（敌方 AI 会逐步演示） |
| `M` | 开关音效 |
| `T` | 开关**敌方威胁范围** —— 显示所有敌人下回合能打到的每一格 |
| `Esc` / 右键 | 取消选择 |
| `R` | 重开本关 |
| 侧边栏「← 返回关卡列表」 | 中途退出（当前局面自动存进"未完成对局"槽位） |

**单位卡片会显示它装备的武器**（名字 + 类别 + 射程 + 暴击率），
攻击力显示的是**已含武器威力**的总值。
战斗预测里"武器相克"那一行只在**有相克关系**时才出现 ——
弓和魔法不入环，跟谁打都不会显示，这是对的。

## 三条铁律

写代码（或者让 AI 写代码）之前，请先接受这三条：

### 1. `src/core/` 里不许出现引擎 API

不许 `import Phaser`，不许碰 `window` / `document`，不许用 `Math.random()`。
core 必须是**纯函数 + 纯数据**。做到这一点，你才能：

- 用 Node 秒级跑完 2000 局对战来调数值；
- 让 AI Agent 写完代码自己跑测试、看红灯、自己修；
- 将来换引擎（或加手机端）时只重写 `game/` 一层。

### 2. 所有状态变更必须走 `applyAction(state, action)`

```ts
this.battle = applyAction(this.battle, { type: 'move', unitId, to });
```

不许直接改 `unit.pos`。这条守住了，存档、回放、联机同步、撤销全部免费。

### 3. 先改 `docs/rules.md`，再改代码

战棋 90% 的 bug 来自"边界情况没定义清楚"，不是算法写错。
规则文档是 AI 迭代时的锚点，没有它必然出现规则漂移。

## 逻辑与渲染的边界长什么样

```ts
// game/BattleScene.ts —— 渲染层想知道"这个单位能走到哪"
const range = computeMoveRange(this.battle.map, this.battle.units, unit);
this.moveKeys = new Set(range.destinations);        // 只用来画蓝格

// 想知道"点这一格合不合法" —— 也问 core，不自己判断
if (this.moveKeys.has(key(tile))) {
  this.dispatch({ type: 'move', unitId: selected.id, to: tile });
}
```

渲染层**一行规则都不写**。它只负责：把 core 算出来的东西画出来，把用户的点击翻译成 Action。

## 用 AI 迭代这个项目

### 推荐的 agent 工作流

1. **让 Agent 自己跑测试，而不是只让它写代码。**
   关键提示词：

   > 先读 `docs/rules.md`。然后用 `pnpm test` 复现问题，改代码直到测试全绿，
   > 最后跑 `pnpm typecheck`。不要修改测试来让它通过。

2. **新增机制的标准流程**（照着 `docs/rules.md` 第 11 节挑）：

   ```
   1. 在 docs/rules.md 补一节，把公式和边界情况写清楚
   2. 在 src/core/ 实现，并加一个 tests/xxx.test.ts 断言文档里的公式
   3. 跑 pnpm test 确认全绿
   4. 最后才动 src/game/ 把它画出来
   ```

3. **数值平衡用模拟器，不要靠手感。**
   ```
   改 combat.ts 的系数 → pnpm sim 2000 → 看我方胜率是不是还在 45%~60%
   ```
   胜率明显偏移，说明数值坏了，不是"感觉不太对"。

4. **给 Agent 的防幻觉提示词：**
   > 只使用 `src/core/index.ts` 导出的 API 和 Phaser 4 官方 API。
   > 不确定的 API 先去 `node_modules/phaser/types/` 里确认真实签名，
   > 不要凭记忆编造方法名。

5. **每个里程碑打 tag。** Agent 改崩了能一键回退。

### 为什么这套架构特别适合 AI

| 架构特点 | 对 AI 协作的意义 |
|---|---|
| core 是纯函数 | Agent 能写单测、跑单测、读报错、自己修，形成闭环 |
| 逻辑不依赖浏览器 | 测试跑在 Node 里，一秒出结果，不用启浏览器截图 |
| 内容是 JSON | Agent 生成关卡/单位不碰代码，出错被 loader 拦住并给出可读报错 |
| 规则有单一文档 | Agent 不需要猜"反击到底怎么算" |
| 有 headless 模拟器 | 数值改动有客观反馈信号，而不是"看起来差不多" |

## 数值调整速查

| 想改什么 | 改哪里 |
|---|---|
| 命中率公式 | `src/core/combat.ts` 的 `HIT_BASE` / `HIT_PER_SKILL` |
| 追击门槛（默认速度差 4） | `src/core/combat.ts` 的 `DOUBLE_THRESHOLD` |
| 暴击倍率（默认 ×3） | `src/core/combat.ts` 的 `CRIT_MULTIPLIER` |
| 武器相克的强弱 | `src/core/weapons.ts` 的 `TRIANGLE_MIGHT` / `TRIANGLE_HIT` |
| 相克关系（谁克谁） | `src/core/weapons.ts` 顶部的 `BEATS` |
| 地形消耗 / 防御 / 闪避 / 回血 | `src/core/terrain.ts` |
| 控制区是否生效（ZOC） | `src/core/pathfind.ts` 的 `computeZoc` / `computeMoveRange` |
| 单位属性 | `data/units.json` |
| 等级成长率（升级时涨什么） | `data/units.json` 的 `growths` |
| 经验给多少 / 升级要多少 | `src/core/progression.ts` 顶部的 `EXP_ON_*` / `EXP_PER_LEVEL` |
| 某一关敌人的等级 | `data/maps/*.json` 里每个 spawn 的 `level` |
| 武器的威力 / 命中 / 暴击 / 射程 | `data/weapons.json` |
| 关卡地形与布阵 | `data/maps/*.json` |
| 关卡顺序与解锁 | `data/campaign.json` |
| AI 权重（激进/保守） | `src/core/ai.ts` 顶部的 `W_*` 常量 |
| 格子像素大小 | `src/game/theme.ts` 的 `TILE` |
| 配色 | `src/game/theme.ts` 的 `COLORS` |

**改完记得同步 `docs/rules.md`，然后跑 `pnpm sim` 确认三关胜率都没跑偏。**

> ⚠️ 改武器时留意：**射程是武器的属性，不是职业的。**
> 想让弓手能打 3 格，改 `data/weapons.json` 里 `short-bow` 的 `range`，不要去改单位。

## 加一张新地图

1. 复制 `data/maps/plain-01.json`，改 `id` / `name` / `terrain` / `spawns`。
2. 在 `src/game/levels.ts` 顶部的 `RAW_MAPS` 里登记一行 import + 一条映射。
3. 在 `data/campaign.json` 的 `levels` 里加一条 `{ id, name, brief }`，`id` 要和文件名一致。

第 2 步会让人觉得多余（为什么不自动扫 `data/maps/` 下的所有文件？），
原因见「已知的坑」第 11 条：自动扫描要用 `import.meta.glob`，而它是 Vite 专有的，
会让 `pnpm sim` 直接崩。**显式登记换来的是所有工具链都能加载关卡。**

漏了第 2 步或第 3 步都不会静默失败：
`LevelRegistry` 在构造时会把战役和地图交叉校验一遍，启动就报错并列出缺了哪个。
画布尺寸会自动跟着地图走，不需要改任何尺寸常量。

`loader.ts` 会在启动时校验：地形行数/列数、地形名称是否合法、出生点是否越界/重叠/落在水里、`team` 是否合法。**报错信息会直接指出是第几行第几列。**

## 表现层怎么做的（M2）

`core` 一行都没动。演出需要的一切都是从「动作前的状态」和「动作后的状态」里推出来的：

```
applyAction(before, action) ──► after
                                  │
        buildFeedback(before, after, action)   ← 纯函数，有 12 个单测
                                  │
                            FxEvent[]            ← 该演什么（数据）
                                  │
                          playFeedback(...)      ← 怎么演（Phaser）
```

分三层是因为**前两层能在 Node 里断言**，只有最后一层需要人眼。

### 关键难点：怎么知道是哪一下落空了

HP 差值只能告诉你「总共掉了多少血」，无法区分
「第一下命中 + 第二下落空」和「第一下落空 + 第二下命中」——飘字顺序会错。

解法是**用 core 已经导出的纯函数把这次交战重放一遍**：

```ts
planStrikes(map, attacker, target)   // 拿到完整打击序列
rollPercent(seed, cursor, hit)       // 用同一个种子重放每一次掷骰
```

重放完拿结果和真实的 `after` 状态**对账**（双方 HP + 随机游标），
对不上就返回 `null`，退化成「只显示 HP 差值」。
所以就算将来 `core/combat.ts` 的结算逻辑改了而这里忘了跟，
**表现层也只会变笨，绝不会显示错误的数字**。

### 演出期间的输入锁

加入异步动画后必须补上的一环：`busy` 标志。
没有它，玩家能在敌方突进到一半时点走自己的单位，画面和状态就脱节了。
同理还有 `runId`——玩家中途按 `R` 重开时，旧的回放计划必须自己作废。

## 已实现的功能

### M2：表现层

- **伤害飘字** —— 普通伤害 / 击杀（更大更红）/ 落空（MISS）
- **攻击运镜** —— 镜头推近交战双方，打完自动退回原位
- **突进** —— 出手方朝目标突进再退回，结束时精确归位
- **受击反馈** —— 单位抖动 + 冲击波圈 + 镜头震动（击杀时更重）
- **阵亡动画** —— 血条先掉到 0，再淡出 + 缩小 + 倾倒
- **沿路径行走** —— 走 Dijkstra 回溯出的真实路线，不再穿墙穿水
- **血条平滑过渡** —— 不再是瞬间跳变
- **阶段 / 胜负横幅** —— 用 DOM 做的，不受镜头缩放影响
- **音效** —— 12 种音色，全部用 WebAudio 现场合成
- **敌方威胁范围**（按 `T`）—— 见 M3

### M3：敌方威胁范围

玩家需要回答一个问题：**"我把人放这儿，下回合会不会挨打？"**
没有这个功能就只能一格一格数敌人够不够得着。

关键在语义：**不是"以当前位置能打到哪"，而是"先移动、再攻击"能覆盖到哪**。
所以要把每个敌人的移动范围整个展开，再从每个落脚点算一遍射程，最后求并集。

```
computeThreatZone(state, 'enemy')   // 纯函数，7 个单测
```

渲染上刻意和已有的红色攻击范围**区分开**：威胁范围是**一片区域**，
所以只画淡填充 + **外轮廓**（逐格描边会和攻击范围的方框糊成一片）；
攻击范围是**点状信息**，保持亮红 + 每格描边并盖在上面。

默认关闭 —— 它盖住的面积很大，一直开着整张棋盘会很吵。
另外缓存了结果：`refresh()` 在鼠标移动时就会触发，而重算一遍要对每个敌人跑一次 Dijkstra。

### 音效为什么不用素材文件

`src/game/audio.ts` 用振荡器 + 带通噪声合成全部音效。对独立开发这是实打实的省事：
不用找素材、不用管授权、不用转格式、包体一个字节不增加、改一个数字就换音色。

关键是**配方表是纯数据**，所以这部分也能单测（12 个断言）：

```ts
export const SFX: Record<SfxName, SfxRecipe> = {
  hit: {
    noise: [{ freq: 1500, to: 320, q: 1.1, dur: 0.11, gain: 0.2 }],
    tones: [{ wave: 'square', freq: 190, to: 80, dur: 0.11, gain: 0.16 }],
  },
  lethal: { /* 同一个思路但更重更长 */ },
  // …select / confirm / whoosh / miss / phase / win / lose / deny
};
```

测试断言的不是"好不好听"（那是耳朵的事），而是**合法性**和**相对轻重符合设计意图**：
击杀要比普通命中重、落空要比命中轻、战斗音不能被交互音盖过。
这些正是改配方时最容易不小心弄反的地方。

顺带修掉一个隐蔽的类型坑：`ctx` / `master` 是外层 `let`，在多次函数调用之后
TypeScript 会取消对它们的收窄，直接往下用会报"可能为 null"。
`play()` 里先抄进 `const` 局部量就稳了。

### M4：关卡选择与存档

**三张关卡**（`data/campaign.json` 定顺序和简介，地图各自一个 json）：

| 关卡 | 设计意图 | 我方 | 敌方 |
|---|---|---|---|
| 1. 边境平原 | 开阔地，熟悉移动/攻击/地形 | 剑士×2 + 弓手 + 术士 | 山贼×3 + **山贼枪兵×2** + 贼弓手 |
| 2. 迷雾森林 | 中路封死，只能从上下两翼的林带推进 | 同上 | 贼首 + 山贼×2 + **山贼枪兵** + 贼弓手 |
| 3. 峡谷要塞 | 敌人据要塞（防 +3 / 闪避 +30 / 每回合回 3）凭险固守 | **+重骑** | 贼首 + 巫医 + 山贼×2 + **山贼枪兵** + 贼弓手 |

⚠️ **敌方阵容里的武器搭配是刻意的，不是随便配的。**
剑士用剑，山贼用斧（被剑克），山贼枪兵用枪（克剑）。
如果敌人清一色是斧头，玩家的剑就是白送 —— 见下面「武器相克上线后」。

**进度**（`src/core/campaign.ts`，纯函数、19 个单测）：
第一关永远开放，之后每关要求前一关通关。战绩只保留**更好**的一次
（先比残存人数，再比回合数）—— 否则玩家重打一次失误反而把记录刷差了。

**存档**（`src/game/storage.ts`）：`localStorage`，存进度 + 一个"中途对局"槽位。
每次动作后自动写一次，所以随时关掉浏览器都能接着打。

这一层最值得说的是**它的容错**。存档是外部输入（用户能改、版本会变、
隐私模式下根本写不进去），所以：

- JSON 损坏 / 版本号不匹配 → 丢弃重来，绝不带着半截数据崩掉
- `inProgress` 结构不对 → 只丢它，通关进度保留
- 写入抛异常（配额满）→ 退化成内存存储，这一局照常能玩
- 拿不到 `localStorage`（隐私模式、`file://`）→ 界面上明说"进度不会保存"

`createSaveStore` 只依赖 `getItem` / `setItem` 两个方法（`StorageLike`），
所以测试里塞个假对象就够 —— 不需要 jsdom，也不需要真的浏览器存储。

### M5：武器系统、相克与暴击

**这次改动的核心是把"射程"从职业挪到武器上。** 以前 `range` 和 `canCounter`
是单位模板上的字段，于是"弓手只能打 2 格"这件事是**硬编码**的。
现在 `unit.weapon.range` 是唯一来源，`canCounter` 这个字段**直接删掉了** ——
弓手在距离 1 打不到人，所以自然反击不了。少一个字段就少一处数据不一致。

**武器相克（武器三角）**：

```
剑 > 斧 > 枪 > 剑        弓和魔法不入环
```

占优时 **+1 攻击力 / +10 命中**，不利时反过来。
它让"打谁"变成一个真实的选择，而不是"谁近打谁"。

**六把武器的性格**（具体数值在 `data/weapons.json`，这里只记设计意图）：

| 武器 | 类别 | 性格 |
|---|---|---|
| 铁剑 | 剑 | 命中最高 + 能会心，威力偏低 → "可靠" |
| 铁枪 | 枪 | 三项都居中 → "万金油" |
| 铁斧 | 斧 | 威力最大但最不准、不会心 → "赌一把" |
| 短弓 | 弓 | **射程 2**、命中高、能会心，但被贴脸时无法还手 |
| 火球术 | 魔法 | **射程 1~2**，唯一能远距离反击的武器，威力中上 |
| 暗咒 | 魔法 | 射程 1~2，略弱于火球术，给敌方的巫医用 |

剑 / 枪 / 斧三者的"总价值"要大致相等 —— 改数值时别让某一把全面碾压。

**暴击**：暴击率**只看武器**（剑和弓 6%，斧枪魔法 0%），伤害 ×3。
刻意不掺技巧 —— 掺了就意味着每次交战多掷一次骰，命中率分布全乱，
而且"同一局面必然得出同一结果"更难验证，而那是整个项目可复现性的根基。

**要塞回血**：回合开始时站在要塞上回 3 点。这让"守着要塞"从一个纯防御加成
变成真实的战术选择。

**顺手做掉一个架构隐患。** 表现层的战斗重放原本是照着 `resolveCombat`
重写一遍循环，靠一个"对账检查"兜底。加入暴击骰之后那种写法必然出事
（掷骰次数变了，随机游标推进方式就变了），所以把结算抽成共用的纯函数
`simulateCombat()` —— 现在**真实结算和演出重放调的是同一个它**，不可能对不上。

### M5 续：控制区（ZOC）

**踏入敌人相邻格的瞬间，移动立刻结束** —— 那一格能站，但不能从它继续往外走。

效果是每个单位实际封住的不再只有脚下 1 格，而是周围一圈：
**三个并排的单位能封住一条 5 格宽的通路**。没有它的话，任何防线都能被一步绕过去。

实现只有一行关键代码 —— 在 Dijkstra 里，写入 cost/prev 之后判断：

```ts
costs.set(nk, total);
prev.set(nk, cur.k);
if (zoc.has(nk)) continue;   // 能站，但不能从它继续走
heap.push({ k: nk, cost: total });
```

⚠️ **起点不检查控制区。** 已经在敌人身边的单位必须能脱离，
否则被贴住一次就永远动不了 —— 那是"麻痹"，不是"控制区"。

界面上，移动范围会分成两段：**蓝色**是能自由走动的格子，
**琥珀色**是"踏进去就停"的控制区落点。规则不用解释也看得懂。
光标停在琥珀格上时，侧边栏会说明原因。

**这个机制直接暴露了两个藏了很久的 bug**，见下面「ZOC 掀出来的两个僵局」。

### M6：经验值与升级成长

**从"打完就没了"变成"角色会变强"。** 数值见 `docs/rules.md` 5.7 / 5.8，
这里只说三件值得记住的事。

**① 升级掷骰必须写在 core，而且必须写在 `simulateCombat` 里面。**

它消耗随机游标。如果把它挪到战斗之外（比如"打完再单独结算经验"），
那 `replayCombat` 的对账立刻碎掉 —— 演出重放算出来的游标和真实结算对不上，
飘字顺序就全乱了。所以经验结算和打击结算共用同一条路径：

```
打击（命中 → 暴击）→ 攻方经验 → 守方经验
```

**② 等级必须真的带属性，否则它是正反馈。**

我第一版只给敌人写了 `level: 3`，但属性还是模板值。结果第三关胜率
**从 63.6% 飙到 87.3%**、通关率 85% —— 因为等级只影响经验公式，
敌人等级越高，玩家吃到的等级差经验越多，玩家滚雪球。

修法是 `statsAtLevel()`：**等级 N 的白板属性 = 模板 + 成长率期望值 × (N−1)**。
敌人用期望值向下取整（确定性的），我方走掷骰并有实际结果要保存。

**③ 成长要跨关卡带下去，而这需要一个新的模拟器来验证。**

名册（`Progress.roster`）按**稳定槽位名** `soldier#0` 存等级/经验/五项属性。
不能用战场实例 id —— 那里面含出生点下标，换张地图就变了。

关键是：**`pnpm sim` 每关都用全新队伍，看不见成长。** 所以加了 `pnpm campaign`，
它从第一关一路打到第三关、带着名册：

| | 第一关 | 第二关 | 第三关 | 通关率 |
|---|---|---|---|---|
| **带成长（真实战役）** | 91.8% | 74.1% | 63.6% | **43.3%** |
| 独立跑（白板队伍） | 92.0% | 59.6% | 26.8% | — |

**这张表就是升级存在的意义**：不带成长时关卡从 92.0% 一路掉到 26.8%；
带成长时平缓降到 63.6%。进关等级 1.0 → 1.5 → 2.7，出关 1.5 → 3.1 → 4.3。

### 等级上限为什么只有 10

第一版我把上限设成 20，结果 `pnpm stall` 抓到第三关有 0.03% 的对局永远打不完。
把局面打出来一看：

```
P 重骑 Lv18  攻 17  防 15  速 8   技 10   地形 fort
E 贼首 Lv20  攻 18  防 12  速 14  技 16   地形 fort
```

- 重骑打贼首：伤害 `17 − (12+3) = 2`，命中 `60 + (10−14)×5 + 10 − 30 = **20%**`
- 贼首打重骑：伤害 `18 − (15+3) = **0**`

**双方都几乎打不动对方**，而且这是一个**自我强化的循环**：
僵局拖长 → 双方狂吃等级差经验 → 顶到 18/20 级 → 属性进一步拉平 → 更打不动。

根因是**高等级时 HP 和防御涨得比伤害快**：武器威力固定 3~6，
而 HP 成长 60~80%、防御成长 25~50%。两处修：

1. **等级上限 20 → 10。** 让数值曲线留在能出结果的区间里。
2. **等级差经验封顶 5 级。** 不封顶的话，一场拖长的战斗里双方互相攻击几十次，
   每次都按"敌人比我高 19 级"结算 —— 那是一台失控的发电机。

> **教训：加"成长"这类机制时，一定要跑长时间模拟并且把僵局局面打出来看。**
> 0.03% 的僵局率在统计表上完全看不出来，但它意味着**真实玩家会永远卡住**
> （游戏没有回合上限）。而且这次的两个原因互为因果，光看数字根本猜不到。

### M5 续：AI 集火

**每个单位行动前，全队先重算一次"这回合该咬住谁"**，打这个目标的选项额外 +60 分。

在此之前每个单位独立打分，于是五个敌人各打各的 —— 每人蹭掉你 6 点血，
一轮下来谁都没死。玩家感受到的是"敌人不痛不痒"。现在伤害会叠在同一个人身上，
**逼你认真保护后排** —— 这也是 ZOC 的另一半：ZOC 让你挡得住，集火才让"挡"值得做。

**目标评选**按优先级：全队能合起来打死的（+500）> 已经受伤的（每点血 +3）>
攻击力高的（×4）。**够不着的敌人直接排除**，否则"远处那个头目攻击力最高"
会把全队往错误的方向引。

估算用**粗略伤害**（`mov + 射程` 的曼哈顿距离近似可达性，不算地形和命中）——
选集火目标不需要精确，只需要排出相对顺序。好处是它很便宜，
所以**每个单位行动前都能重算一次**，目标会随着敌人掉血、阵亡自动切换。

**平衡影响**（战役模拟，各 400 局）：

| | 集火前 | 集火后 |
|---|---|---|
| 第一关 | 93.5% | 90.8% |
| 第二关 | 78.9% | 74.4% |
| 第三关 | 74.6% | 70.4% |
| **通关率** | 55.0% | **47.5%** |

> ⚠️ **模拟器测不准这次改动。** 它让 AI 同时接管双方，所以集火对两边一起生效，
> 数字只反映"纸面实力"的净变化。而它对**人类玩家**的影响是不对称的：
> 你本来就会集火，现在敌人也会了。真实体感变化比这张表大。

顺带发现一条规律：**集火对"人多的一方"收益更大** —— 能叠的伤害更多。
本作敌人 5~6 个单位、我方 4~5 个，所以开启集火后玩家胜率是下降的。

### M6 续：武器切换

单位可以携带**多把**武器（`weaponIds`，第一把默认装备）。**换武器不消耗行动** ——
换完照样能移动和攻击，而且**已经行动完的单位也能换**。

> 那它凭什么是"决策"而不是"随手选最优"？因为**装备会一直保持到敌方回合**，
> 而它决定了你能不能反击。真正的选择是"**用哪把武器迎接下一轮**"。

**射程是最直接的收益**：弓手带短弓（2 格、准）和长弓（2~3 格、威力低命中低），
"站 2 格还是 3 格"于是变成和站位绑定的选择 —— 远一格意味着近战完全够不着你，
代价是伤害和命中更低。

**AI 也把武器放进了搜索空间**（`bestAttack` 枚举 落点 × 武器 × 目标），
所以它会自己用上射程和相克，不需要各写一段逻辑。顺序：先换武器 → 再走位 → 最后出手。

顺带修了一个**正确性问题**：威胁范围原本按"当前装备的射程"算，
但敌人可以在出手前换武器 —— 那会低估危险。现在按**携带武器里最大的射程**算。

### ⚠️ 一个做砸又收回来的设计：手斧

我一开始给山贼和重骑都配了**手斧**（近战武器，射程 1~2），想让"射程选择"更普遍。

结果平衡直接炸掉，而且是**结构性**的：

| | 加手斧前 | 加手斧后 |
|---|---|---|
| 第一关 | 92.1% | 82.3% |
| 第二关 | 55.5% | **23.0%** |
| 第三关 | 40.4% | **73.3%** |
| 第三关平均回合 | 11.6 | **15.3** |

**手斧会退化成无限白嫖。** 反击只看向对于攻击方的射程，而本作**没有武器重量、
没有耐久** —— 于是一个高防单位可以永远站在 2 格外免费输出，谁都打不到它。
回合数暴涨就是证据。第二关（森林、移动力减半）玩家的近战追不上，直接崩到 23%；
第三关玩家有重骑（防高），反过来碾压到 73%。

**要引入这类武器，得先有"重量"（拖慢速度、让你被追击）或"耐久"来约束它。**
所以本轮把 1~2 射程的近战武器整个砍掉了，"射程选择"只留给弓手
—— 弓手脆，天然自我限制。

> **教训：一个看起来只是"多一种选择"的武器，可能把反击规则撕开一个口子。**
> 加武器之前先问一句：**"有没有单位能永远站在它的射程里，而对方够不着？"**

### M6 续：增援

地图可以声明"第 N 回合来一波"：

```json
"reinforcements": [
  { "turn": 4, "spawns": [{ "defId": "bandit", "team": "enemy", "x": 0, "y": 0, "level": 3 }] }
]
```

**作用不是"变难"，而是惩罚龟缩。** 没有增援时玩家可以靠着要塞回血慢慢磨，
有了增援就必须往前推。它也让一关内部有节奏：前几回合安静，然后压力上来。

- 第二关：第 4 回合，1 个山贼从**玩家后方**进场
- 第三关：第 4 回合，1 个山贼从东侧进场

**架构上有一条硬约束，值得单独说：** `endTurn` 是纯函数，签名是 `(state) => state`，
拿不到 `defs` / `weapons` 两张表。所以增援单位**在开局就全部造好**
（`UnitBlueprint`：属性、等级、武器都就绪，只差 `id` / `pos` / `slot`），
以 `pendingReinforcements` 的形式放进 `state`，到场时只补身份字段。
代价是存档里带上这些"还没上场"的完整单位数据 —— 换来 `endTurn` 仍然纯、可单测、可回放。

**到场格被占时挪到最近的空格，而不是延期到场。** 延期会被玩家用身体堵住刷兵点来利用。
最近空格的扫描顺序固定（逐行逐列 + 严格小于），所以完全确定、可回放。

### ⚠️ 顺带挖出来的一个真死循环：伤害下限

加了增援之后，第三关出现了 **1/2000 局的僵局**。我先用 A/B 对照确认责任：

```
fort-01   有增援：1 局僵局（seed 245）   无增援：0 局   ← 确实是我引入的
```

然后追下去，发现它**不是"慢"，是真的永远打不完** —— 跑了 1000 回合仍在继续：

```
重骑 攻 13 → 贼首 防 10 + 要塞 3 = 13  → 伤害 0   命中 25%
贼首 攻 15 → 重骑 防 13 + 要塞 3 = 16  → 伤害 0   命中 43%
```

**双方伤害都恰好是 0**，于是永远互相挥空。原式 `max(0, 攻 − (防 + 地形))`
允许双方同时为 0，而那是无法取胜的状态。它极其罕见，但**只在刀刃上** ——
攻防差 1 点就完全正常，所以靠调数值几乎不可能避开。

增援只是"给了重骑更多经验、让它长到 13 防"，正好卡上这个刀刃。**根因在战斗公式里，不在增援。**

修法是**伤害下限 1**：

```
伤害 = max(1, 攻击力 + 相克修正 − (防御 + 地形防御))
```

配合已有的"被贴住的单位不能回血"，就**从数学上保证了任何对局最终都能分出胜负**：
挨打的一方至少掉 1 点，而且只要还在交战就回不了血。

代价是"打不动"的局面消失了，高防单位不再不可战胜 —— 这是刻意的：
本作没有破甲、没有背刺，如果还存在伤害为 0 的对局，玩家只能干看着。

结果：**三关各 2500 局，0 / 0 / 0 僵局**，而且平均回合数还降了（12.9 → 11.4）。

### M6 续：关卡目标

到这一步之前，三关的**玩法其实是同一个** —— 区别只有地形和敌人配置。
现在每关有自己的胜利条件：

| 关卡 | 目标 | 玩起来的变化 |
|---|---|---|
| 1 边境平原 | 全灭（兜底） | 教学关保持简单 |
| 2 迷雾森林 | **击破贼首** | 从"被森林消耗到死"变成"突破隘口直取头目"，不必打光所有人 |
| 3 峡谷要塞 | **守住 8 回合** | 从"磨死对面"变成"在围攻下扛住"，位置本身就是目标 |

**"全灭敌人"是所有关卡的兜底胜利条件** —— 打得比目标更彻底，没理由不算赢。
所以 `objective` 实际描述的是"除了全灭之外，还能怎么赢"。

第 3 关选"守住"而不是"占领据点"是有意的：**它不需要任何新的 AI 逻辑**
（"打敌人、别死"本来就是守住的行为），而占点要求 AI 会寻路前往指定格子，
那个行为现在完全不存在。而且它还有个附带好处：**把对局长度硬性封顶在 8 回合**，
从结构上杜绝了这一关出现打不完的局。

⚠️ **AI 也必须懂目标，否则模拟器测出来的胜率是假的。** 如果目标是"击破敌将"
而 AI 不知道，它会照着"谁脆打谁"把敌人清光 —— 那也能赢（全灭兜底），
但它根本没在玩这一关的目标。所以 `pickFocusTarget` 里给目标兵种加了权重 800，
比"能击杀"（500）还大。

**围攻要有围攻的样子。** 第一版"守住 8 回合"实测 **73.2%**（战役里 93.5%）——
要塞回血 + 5 个单位守 8 回合对 AI 来说太轻松。加密波次（第 2/4/6 回合各来一波）
并给敌人加一档等级之后：

| | 第一关 | 第二关 | 第三关 | 通关率 |
|---|---|---|---|---|
| 改目标前 | 91.9% | 41.5% | 28.4% | 48.3% |
| 改目标后（波次太轻） | 91.9% | 48.8% | 73.2% | 68.0% |
| **定稿** | 91.6% | 48.9% | **30.6%** | — |
| **定稿（带成长）** | 91.8% | 79.3% | **70.8%** | **51.5%** |

**这是这个项目第一次出现单调递增的难度曲线**（91.8 → 79.3 → 70.8）。
在此之前"第二关比第三关难"是常态，因为三关的目标完全一样、只有数值差别。

### M5 续：战技

**战技 = 一次带修正的攻击**，走的是同一个 `attack` 动作 + `skillId`，
不是独立的一套动作系统。侧边栏按 **Q** 切换，预测会实时跟着变。

**它的核心设计不是"资源换伤害"，是"不能追击"：**

```
普通攻击：威力 a，打两下（速度差 ≥ 4 时）
战技：    威力 a + 修正，只打一下，消耗 TP
```

没有这一条，战技只是"花资源换伤害"，**永远该用**，决策退化成"资源够不够"。
有了它才构成真正的取舍：

- 打**高防目标** → 第二下往往只有 1~2 点，不如一次重击打穿 → **用战技**
- 打**软目标** → 两下普通攻击总伤害更高 → **别用**

三个战技（`data/skills.json`）：

| 战技 | TP | 修正 | 定位 |
|---|---|---|---|
| 重击 | 20 | 威 +6、中 −10 | 破高防 |
| 瞄准 | 15 | 中 +30 | 打森林/要塞里的高闪避目标 |
| 致命一击 | 25 | 暴 +40、威 +2、中 −5 | 赌一把 |

修正**一正一负是刻意的**，而且加载期会拒绝"三项修正全为零"的战技 ——
那等于"花 TP 做普通攻击"。

**TP 收支**：上限 100；**开局自带 30（仅玩家方）**；自己回合开始 +5；**命中一次 +8**（攻守双方都算）。
只奖命中不奖出手，否则乱打也能攒资源。**TP 不进名册** ——
它是"这一局里的进攻资源"，跨关累积会让后期每一场都变成技能倾泻。

> ⚠️ **开局自带 TP 这件事我一开始做错了，值得记一笔。**
> 第一版 TP 从 0 开始，结果你按 Q「什么都没发生」—— 因为最便宜的瞄准（15）
> 要到第 4 回合才买得起，而第一关平均只打 **6.7 回合**，整个系统几乎露不了面；
> 而且当时的实现发现"没有可用的战技"就**静默返回**，没有任何反馈。
> 我第一反应也是"功能坏了"。
>
> 改成开局发 30 点之后又踩了第二个坑：**敌人也拿到了 30 点**，
> 而敌人有 5~6 个单位、在同一个阶段里连续行动，等于开局一次协调齐射 ——
> 通关率从 44.3% 砸到 **31.3%**。改成**只发玩家方**，回到 **43.3%**，
> 代价几乎为零而机制立刻可见。敌人照常每回合 +5、命中 +8，
> 打到第 3~4 回合一样会开战技，只是不会开场糊脸。

### ⚠️ 一个差点写错的结算顺序

"扣消耗"和"命中回复"必须基于**同一份战果**来算，所以两件事都放在 `resolveCombat` 里：

```
tp=95，上限 100，消耗 20，命中 1 次
正确：95 − 20 + 8 = 83
错误：min(100, 95 + 8) − 20 = 80     ← 凭空少 3 点
```

分两处写的自然写法就是错的（回复先被上限夹住再扣消耗）。这和
"经验值必须在同一个函数里结算"是同一个道理 —— **凡是有上下限的资源，
加减顺序就是有语义的**。这条写成了单测。

### 顺带修掉一个上一轮引入的真 bug

`BattleScene.selectedUnit()` 会把 `done` 的单位过滤掉。我上一轮做了"打完还能换武器"，
但 `equipWeaponAt` 用的是 `selectedUnit()` —— 拿到 `null` 之后**一声不响地 return**，
所以**那个功能实际上从来没生效过**。

修法是加一个 `inspectedUnit()`（不过滤 `done`，语义是"当前在看的单位"），
换武器 / 选战技用它，`selectedUnit()`（语义是"还能不能接受指令"）保持原样。
两个方法并存在代码里留了注释说明区别 —— **这种"静默 return"型的 bug
不会报错、不会崩，只是功能静悄悄地不工作**，比崩溃难查得多。

### 平衡影响：战技让难度上升了

| | 第一关 | 第二关 | 第三关 | 通关率 |
|---|---|---|---|---|
| 加战技前 | 91.8% | 79.3% | 70.8% | 51.5% |
| **加战技后** | 89.0% | 78.7% | **63.2%** | **44.3%** |

**影响是不对称的**：模拟器里双方都会用战技，但第三关是"守住 8 回合"，
**会开战技的敌人对防守方伤害更大**。第一、二关几乎没动。

> 注意这张表低估了人类的强度 —— 模拟器里的 AI 对 TP 有 `W_TP = 1` 的保守惩罚，
> 会放过"赢得不明显"的战技。人类玩家不会有这个犹豫。

如果觉得偏难，最省事的补偿是把 `data/skills.json` 里敌人的战技去掉
（`data/units.json` 里 `bandit` / `shaman` / `brigand-archer` 的 `skillIds` 清空），
只留玩家侧 —— 但那样"敌人也会开大"这个压力感就没了。

## 数值平衡是怎么调出来的（已完成）

### 改前：结构上不可能输

`pnpm sim` 是我方 **100% 胜**，其中 68% 零阵亡，剑士在 800 次出场里**一次没死过**。

算伤害经济就知道为什么：双方总血量几乎相同（86 vs 85），
但我方期望输出是敌方的 **2.1 倍**（20.7 vs 9.8）。

问题在于山贼是"弱化版剑士"—— 血量、攻击、防御、速度、技巧、移动力**每一项都不如**，
还额外少了先手和两个远程单位。没有任何一个维度能翻盘。

### 改法：不是把玩家改弱，是让敌人换个活法

| | 玩家 | 敌人 |
|---|---|---|
| 人数 | 4 | **6** |
| 定位 | 精锐：血厚、命中高、有法师 | 莽夫：**攻高防低**，靠数量 |
| 山贼 | — | `hp 20 / 基础 atk 5 / def 2`（原 `22 / 8 / 3`） |

改完双方伤害是对称的（士兵打山贼 7 点，山贼打士兵 6 点），
差别只在**血量、命中率和人数**上 —— 这才是干净的"以质换量"。

> 上面的 `atk` 是**基础值**。M5 引入武器后，实际攻击力 = `atk + weapon.might`，
> 山贼是 `5 + 铁斧 6 = 11`。

### 结果

**第一关**（2000 局，改前 vs 改后）：

| | 改前 | 改后 |
|---|---|---|
| 我方胜 | 100% | **76.6%** |
| 平均残存 | 3.7 / 4 | **1.6 / 4** |
| 胜局中零阵亡 | 68% | **6.8%** |
| 剑士存活率 | 100% | **38%** |

**三关各自独立跑**（各 800 局，**队伍都是白板 1 级**）：

| 关卡 | 我方胜 | 平均残存 | 平均回合 |
|---|---|---|---|
| 1. 边境平原 | 92.0% | 2.5 / 4 | 6.1 |
| 2. 迷雾森林 | 59.6% | 1.4 / 4 | 8.6 |
| 3. 峡谷要塞 | 26.8% | 0.4 / 5 | 7.1 |

⚠️ **这张表不是真实的游戏体验** —— 它假设你每关都从 1 级重新开始。
真实战役里队伍会成长，第三关是 76% 不是 43%，见上面「M6」那一节的对照表。
`pnpm sim` 量的是**关卡的绝对难度**，`pnpm campaign` 量的才是**玩家会遇到的难度**。
两个都要看。

（M4 时独立跑是 75.3 / 74.3 / 66.9。曲线一路变得这么陡，是因为后面加的
武器相克、ZOC、敌人等级都让关卡本身更难了 —— 而升级正是为了把这条陡坡拉平。）

⚠️ **第一关 92.5% 是有意的，也是目前唯一偏软的一关。**
它现在的职责是教会你 ZOC —— 数据说明它做到了：
**弓手存活率 20% → 65%、术士 → 78%**，也就是"把脆皮藏在剑士后面"这件事真的有效了。
想让它更难，注意**旋钮很粗**：加一个敌人会直接掉到 66.8%（比第二关还难），
所以真要调得从单个敌人的强度或站位下手，不能动人数。

### 武器相克上线后：第一关胜率跳到 99.8%

M5 加完武器相克，第一关从 75.3% 直接飙到 **99.8%**。**这不是 bug，是内容没跟上机制。**

当时的敌方阵容是**清一色斧头**，而玩家有两个剑士。于是每一次交换：

| | 玩家剑士打山贼 | 山贼打玩家剑士 |
|---|---|---|
| 伤害 | 9 + 1 − 2 = **8** | 11 − 1 − 4 = **6** |
| 命中 | 60 + 5 + 12 + 10 = **87** | 60 − 5 + 7 − 10 = **52** |

相克的 ±10 命中、武器的命中差（剑 12 / 斧 7）、暴击（剑 6% / 斧 0%）
三项叠在一起，玩家每次交换都白赚一大截。

> **教训：相克机制只有"两边都有多种武器类型"时才是选择，一边倒就只是白送。**
> 加机制的同一批改动里必须把内容一起改，否则数值会瞬间失衡。

两处修：三角命中从 ±15 降到 ±10，以及给敌人加**山贼枪兵**（用枪，克剑）。
改完 82.1% —— 比 M4 略高，但那多出来的部分是暴击带来的方差，可以接受。

顺带踩到第二个坑：**要塞回血一度定成 5 点，结果第三关出现 1.7% 打满 50 回合的僵局。**
本作常规伤害是 5~8 点，回血 5 意味着站在要塞上的单位每回合净掉 0~3 点血，
1v1 就永远打不完。

> **教训：回血数值和伤害是同一个量纲，一旦接近，防御方就变成了不可杀死。**
> 而且这种 bug 只会以"偶尔打不完"的形式出现 —— 后面会看到它还有更隐蔽的形态。

### ZOC 掀出来的两个僵局

ZOC 上线后第三关的僵局率从 0.8% 涨到 2.3%。我写了个 `pnpm stall`
把僵局局面直接画出来 —— 一画就明白了：

```
    P 重骑     (5,2)  hp 17/30    ← 站在要塞上
    E 山贼     (5,3)  hp 6/20     ← 也站在要塞上
```

重骑（枪）打山贼（斧），**斧克枪** −1；山贼在要塞上防 +3：

| | 伤害 | 命中 | 期望/回合 |
|---|---|---|---|
| 重骑打山贼 | 11 − 1 − 5 = **5** | 60 − 10 − 30 = **30%** | **1.5** |
| 山贼回血 | — | — | **+2** |

**回血比伤害还快，防守方在数学上不可杀死。** 这不是数值没调好，是规则组合的漏洞。

修法不是在"防御 / 闪避 / 回血"三个数字之间继续挪，而是改规则：
**被敌人贴住的单位不能回复。** 要塞仍然是强据点，但要回血就得先脱离接触。
第三关僵局 1.33% → **0**。

**第二个僵局更隐蔽，而且和 ZOC 无关。** 修完上面那个之后第一关冒出来 0.10%：

```
    P 剑士 (5,3)        E 山贼 (5,5)
    .  .  .  ~  ~  ~  ~  .  .  .     ← 中间是湖水
```

两者直线距离只有 2，但中间是水，绕过去要 7 步。AI 的"接近"评分用的是**曼哈顿距离**，
所以它认为"我已经站在最近的落点上了"，于是**永远待机**。

改成按**地形距离**（从所有敌人出发跑一次多源 Dijkstra）之后就好了。
这不只是修僵局 —— 它意味着**AI 以前根本不会绕过任何障碍物**，
只是一直没被发现，因为僵局率只有 0.1%。

三关各 2000 局现在**全部 0 僵局**：

```
关卡 1. 边境平原 · 2000 局 · 僵局 0 局（0.00%）
关卡 2. 迷雾森林 · 2000 局 · 僵局 0 局（0.00%）
关卡 3. 峡谷要塞 · 2000 局 · 僵局 0 局（0.00%）
```

> **教训一：加任何会回血或限制移动的机制之后，都要重跑 `pnpm stall`。**
> 这类 bug 只在"偶尔"出现，看起来就像一局正常的持久战，靠肉眼测不出来。
> 而它的后果很严重：**真实游戏没有回合上限，玩家会永远卡在那里。**
>
> **教训二：贪心 AI 的"接近"评分不能用直线距离。**
> 只要有障碍物，直线距离就会给出错误的方向感，而错误的表现形式是
> "单位站着不动" —— 一个很容易被当成"AI 就是笨"而忽略掉的症状。

### 第二关曾经不可能赢 —— 一个地图设计 bug

第一版第二关的胜率是 **1.3%**，500 局里术士死了 499 次。数值看起来没问题，
所以我去看逐兵种存活率：

| | 术士 | 弓手 | 剑士 | 敌方贼首 |
|---|---|---|---|---|
| 第一关 | 61% | 20% | 40% | — |
| 第二关（旧） | **0%** | 4% | 13% | **74%** |

**问题在地图上，不在数值上。** 第一关中路有湖水挡着，贼首只能绕行；
而我给第二关设计的"隘口"恰好是一条**笔直通向玩家后排的高速公路** ——
术士站在 `(2,4)`，贼首 `mov 5` 两回合就冲脸上了。术士开局就死，
而它正是打高血头目的唯一主力（`atk 12` 对 `def 3` 打 9 点），于是全线崩盘。

把墙移到 `x=5-7`、中路继续用水封死之后：**1.3% → 72.8%**。

> **教训：胜率异常时先看逐兵种存活率，别急着调数值。**
> "某个单位永远活不下来"几乎总是站位或地形问题，而不是它太脆。

顺带一提，头目的设计也是踩出来的。一开始贼首是 `atk 13 / def 5 / hp 30`：

| | 士兵打贼首 | 贼首打士兵 |
|---|---|---|
| 伤害 | 9 − 5 = **4** | 13 − 4 = **9** |
| 需要几刀 | 8 刀 | 3 刀 |

一个贼首 ≈ 三个士兵。而且**把两个山贼换成一个大怪并不是削弱，是集中** ——
一个杀不死的单位每回合都满额输出，玩家的伤害却被分散了。
在我这套规则里（没有破甲、没有包夹），头目的正确定位是
**血厚、攻击中等、防御偏低**的伤害吸收器，而不是一击秒人的怪物。

### 怎么找到这个点的

`pnpm sweep` 一次跑完参数网格，直接看响应曲线：

```
参数                        我方胜      残存(我)
5 敌 / 基础攻 5            98.3%     2.75 / 4
6 敌 / 基础攻 5            82.7%     1.89 / 4     ← 第一关就在这一档
7 敌 / 基础攻 5            45.0%     0.76 / 4
6 敌 / 基础攻 4            96.0%     2.54 / 4
6 敌 / 基础攻 6            70.3%     1.58 / 4
7 敌 / 基础攻 6            32.7%     0.51 / 4
```

调平衡最忌讳"改一个数 → 跑一局 → 再猜"：旋钮和结果不是线性的，靠猜要试十几次。
一次性跑完网格，看着表挑点就行。想扫别的维度就改 `scripts/sweep.ts` 顶部的 `GRID`。

**注意两个旋钮的陡峭程度差很多**：敌人 6→7 掉 37 个百分点，
基础攻 5→6 只掉 12 个。**一个敌人的分量约等于 3 点攻击力。**
所以微调优先动攻击力，动人数是大刀。

> ⚠️ 这个工具的布阵是写死的，**改了游戏内容之后必须回头校准它**。
> M5 加武器相克时我给真实关卡换了阵容，却忘了改这里 ——
> 结果扫描表还在用清一色斧兵，显示"6 敌 96.3%"，而真实关卡是 82.1%。
> 扫描工具和真实关卡用不同阵容时，它给的方向就是错的。

> M5 之后多了武器、相克、暴击三组旋钮，网格要扫的维度变多了。
> 现在的做法是**先看逐兵种存活率定位问题，再决定动哪个旋钮**
> —— 因为大多数"数值不平衡"其实不是数值问题（见上面两个案例）。

### ⚠️ 读这些数字时必须知道的

`pnpm sim` 是**同一套贪心 AI 打自己**。所以：

- **胜率衡量的是"纸面实力差"，不是"玩家有多大概率输"**。
  人比贪心 AI 强得多（会集火、会撤残血、会守隘口、会挑相克），实际胜率会明显更高。
- **越接近 50%，越意味着两败俱伤**。这是对称 AI 的必然结果：一方明显更强就会赢更多，
  所以"势均力敌"等价于"互相消耗到接近全灭"。扫描数据里 50% 那档平均只剩 0.84 人。
- 第一关最终选了 **76.6%**（新手向：第一关应该让玩家熟悉机制，而不是卡关）。
- 第三关目前是 **60.0%**，而且胜局里 56% 只剩 1 人 —— 那是有意的"惨胜"。
- 剩下 **0.8% 的对局打满 50 回合**（模拟器的上限）。那不是死循环，
  而是要塞回血把 1v1 拖成了消耗战；真人玩家不会遇到，因为人会主动换目标。

想调数值就改 `data/units.json`（基础属性）、`data/weapons.json`（武器）、
或 `data/maps/*.json` 的布阵，改完跑 `pnpm sim` 确认。

`tests/harness.test.ts` 里有一条回归测试锁着"胜负都必须出现"，
防止将来谁不小心把平衡改回一边倒 —— **M5 上线时正是它抓住了 99.8% 那次事故。**

### 什么时候做移动端

**等 PC 版 M4 做完之后再考虑。** 到那时你只需要：

1. `pnpm add -D @capacitor/cli @capacitor/core @capacitor/android`
2. `npx cap init && npx cap add android`
3. `pnpm build && npx cap sync && npx cap open android`

`vite.config.ts` 里已经把 `base` 设成 `'./'`，就是为了这一步不出 404。

触屏适配要改的只有 `src/game/BattleScene.ts` 的输入层：
`pointermove` 悬停在手机上不存在，需要改成"点击选中 → 再点确认"。
但你的交互流程**已经就是这个两段式了**，所以改动很小。
侧边栏 HUD 在窄屏上要改成底部抽屉，那是纯 CSS 的活——正好是你最熟的。

## 已知的坑（都踩过一遍了）

1. **`useDefineForClassFields` 必须关掉**（见 `tsconfig.json`）。开着会让 ES2022 的类字段用 `defineProperty` 生成，遮蔽 Phaser `Scene` 原型上的 getter，症状是 `this.input` / `this.add` 莫名其妙变成 `undefined`。
2. **移动范围不是距离。** 用 Dijkstra 按地形消耗算，见 `docs/rules.md` 第 4 节。
3. **攻击范围和移动范围是两回事。** 别用同一个变量存。
4. **先算完状态再播动画。** 见 `BattleScene.runEnemyPhase()` —— 整轮计划先由 core 算完，动画只是事后演示。绝对不要把逻辑塞进 `tween` 的完成回调里。
5. **不要在 core 里用 `Math.random()`。** 回放和测试会立刻失效。
6. **友军可以穿过但不能停留，敌人完全阻挡。** 这条规则改错会让寻路出现"穿人"和"卡死"两种 bug。
7. **`state` 里不许放 `Map` / `Set`。** 会静默破坏 JSON 存档（`Map` 序列化成 `{}`）。
8. **两个 tween 抢同一个属性会互相打架。** 比如走位补间和受击抖动都改 `container.x`，同时跑就会抽搐。本项目的分工是：位置只由 `updateUnitView`（吸附）和 `walkAlong`（逐格行走）负责，抖动只在交战期间发生，两者在时间上不重叠。加新动画前先确认它改的是哪个属性、会和谁重叠。
9. **别在 canvas 里画 UI 文字。** 镜头一旦缩放或位移，canvas 上的字会被一起带偏。侧边栏、阶段横幅这些一律走 DOM —— 顺便还能用 CSS 做动画。
10. **交互规则也必须抽成纯函数。** `selecting` 分支曾经漏掉「点敌人攻击」这一条，导致**不移动就打不了人**，哪怕敌人贴在脸上。core 和 AI 全是对的（AI 的候选落点里含"原地"，所以模拟器也测不出来）—— 纯粹是场景类里漏了一条分支，而那种地方只能靠人手点。现在这类判断全在 `src/game/interaction.ts`，25 个单测锁着，其中一条就是这个 bug 的回归测试。
11. **`import.meta.glob` 是 Vite 专有的，`tsx` 跑脚本时不认。** 关卡注册表一开始想用它实现"丢个 json 就自动加载"，但那会让 `pnpm sim` 直接崩 —— 而模拟器是这个项目最重要的工具。改成显式静态 import，代价是加地图要多写一行，换来的是**所有工具链都能加载关卡**。
12. **别在 canvas 里画列表和按钮。** 关卡选择、结算面板全是 DOM。在 Phaser 里摆这些既费劲又难改，还和侧边栏 HUD 的路线不一致。
13. **加机制的那次改动必须同时改内容，否则数值会瞬间失衡。** 武器相克上线时敌人清一色是斧头，第一关胜率 75% → **99.8%**。机制本身没错，是阵容没跟上。所以**每次加机制之后都要重跑 `pnpm sim` 全部三关**，别只看新写的单测。
14. **回血和伤害是同一个量纲，回血不能接近最低伤害。** 要塞回 5 点、常规伤害 5~8 点 → 站在要塞上的单位每回合净掉 0~3 点血，1v1 永远打不完。第三关因此出现 1.7% 打满 50 回合的僵局。**这种 bug 只会以"偶尔打不完"的形式出现**，不做长时间模拟根本发现不了。
15. **"某个单位永远活不下来"要先怀疑站位和地形，不要先调它的血量。** 第二关曾经 1.3% 胜率，原因是敌首有一条直通玩家后排的高速公路，术士 500 局死 499 次。地图一改就回到 72.8%。
16. **结算逻辑和演出重放必须共用同一个纯函数。** 早先表现层照着 `resolveCombat` 重写了一遍循环，靠"对账检查"兜底；加暴击骰之后掷骰次数变了，那种写法必然错位。现在两边都调 `simulateCombat()`，从结构上消除了这类 bug，而不是靠检查发现它。
17. **改了游戏内容，一定要回头校准模拟器和扫描工具。** `scripts/` 里的布阵是写死的。M5 给真实关卡换了阵容却忘了改 `sweep.ts`，于是扫描表还在用清一色斧兵、显示 96.3%，而真实关卡是 82.1% —— **工具在骗人，而且看起来很有说服力**。`scripts/simulate.ts` 走 `LEVELS`，所以它永远和游戏一致；`sweep.ts` 手搭布阵，所以它需要人盯着。
18. **僵局（永远打不完的对局）必须用工具查，不能靠统计数字。** "未分胜负 1.3%" 完全看不出问题在哪；`pnpm stall` 把棋盘画出来，一眼就知道是谁卡住了谁。**加任何会回血或限制移动的机制之后都要重跑它。**
19. **贪心 AI 的"接近"评分不能用曼哈顿距离。** 隔着水的敌人直线只有 2 格、实际要绕 7 步，用直线距离 AI 会以为"已经到最近了"然后永久待机。改用**地形距离场**（从目标出发跑一次多源 Dijkstra）。症状很隐蔽 —— 表现为"单位站着不动"，很容易被当成"AI 就是笨"。
20. **⚠️ 不要用 PowerShell 的 `Get-Content -Raw` + `Set-Content` 改这个仓库里的文件。** DSH 当前跑的是 **Windows PowerShell 5.1**（`$PSVersionTable` 可以确认），它默认按 ANSI 读写，会把 UTF-8 的中文全部变成乱码、并让文件不再是合法 UTF-8。**改文本一律用编辑工具，不要用 shell。** 万一需要写文件，用 `[System.IO.File]::WriteAllText($path, $text, [System.Text.UTF8Encoding]::new($false))`。这个坑真实发生过一次，`package.json` 被写坏、且因为没有 git 只能手工重建。
21. **加"成长"这类机制时，要问一句"它会不会变成正反馈"。** 等级如果只影响经验公式而不影响属性，那么"敌人更强"反而让玩家升级更快 —— 第三关因此从 63.6% 变成 87.3%，战役直接失去难度。**任何"越强给得越多"的设计都要检查它的方向**（等级差经验、击杀奖励、连击加成都属于这一类）。
22. **跨关卡的数据要用稳定的键。** 名册不能按战场实例 id 存 —— 那里面含出生点下标，换张地图就全变了。要用「兵种 + 同兵种序号」这种与地图无关的槽位名。
23. **单关模拟器看不见成长。** `pnpm sim` 每关都用全新队伍，所以它量的是"关卡绝对难度"；玩家实际遇到的是 `pnpm campaign` 的那条曲线。**两个数都要看，只看一个会得出相反结论**（第三关 43% 还是 75%，取决于你问的是哪个问题）。
24. **等级上限要和武器档位一起设计。** 本作的武器威力固定 3~6，而 HP 成长 60~80%、防御成长 25~50% —— 等级越高伤害越跟不上，高等级单位互相只能造成 0~2 点伤害。上限 20 时会打出僵局，**压到 10 才留在能出结果的区间**。等你加了钢武器/银武器，才有理由把上限放回去。
25. **"越强给得越多"的设计要检查方向。** 等级差经验如果不封顶，一场拖长的战斗能把双方直接顶到满级；而满级又让战斗更打不完 —— 两个 bug 互为因果，光看胜率数字根本猜不到。**加这类机制之后，`pnpm stall` 是必跑的。**
26. **有一类故障单测、typecheck、build 全都抓不到 —— 模块加载期抛错。** 症状是浏览器里 `main.ts` 一行都没跑，页面只剩下 `index.html` 写死的那点静态 DOM（表现为"整页只有一个按钮"），而 Vite 一切正常、250+ 单测全绿。`pnpm smoke` 就是为它写的：用最小 DOM 桩把 `src/main.ts` 真正 import 一遍再断言菜单渲染出来了。**每次改 `main.ts` 的依赖图（新增/删除模块）之后跑一下。**
27. **改了较大的模块图之后，Vite 的 HMR 可能停在半更新状态。** 表现同样是白屏，但代码其实是对的 —— 硬刷新（Ctrl+Shift+R）就好。**先怀疑 HMR，再去翻代码**，否则会在一个不存在的 bug 上浪费很多时间。分辨方法：`pnpm smoke` 通过 = 代码没问题，是运行环境的问题。
28. **写 AI 测试时，ZOC 会让"一个单位够得着两个敌人"变得很罕见。** 我第一版把两个敌人放在近战单位左右两侧，结果那个单位只剩 5 个落点 —— 敌人的控制区把整条通路封死了，它根本走不到第二个敌人旁边。测试看起来像"加分失效"，其实是场景不合法。**改法：用远程单位（射程 2 就不必贴脸），并把敌人拉开到控制区互不重叠。**
29. **断言"合力击杀"时要让命中率封顶**（给攻击方 `skill: 99`）。不然任何一下落空都会把结果从"合力打死"变成"合力打残"，测试就变成在赌 RNG —— 我为此白查了一轮，还差点以为是加分没生效。**凡是断言伤害结果的 AI 测试，先把随机性钉死。**
30. **加武器之前先问："有没有单位能永远站在它的射程里，而对方够不着？"** 手斧（近战、射程 1~2）就是这么把平衡炸掉的：本作没有武器重量、没有耐久，反击又只看得够不够得着，于是一个高防单位可以无限白嫖。**第三关回合数 11.6 → 15.3、第二关胜率 55.5% → 23% 就是它干的。** 一个看起来只是"多一种选择"的武器，可能把反击规则撕开一个口子。
31. **改完数据之后，`pnpm sim` 的每个数字都要看，不要只看胜率。** 平均回合数是最灵敏的"机制坏了"指标 —— 胜率可能只动几个点，而回合数从 11.6 涨到 15.3 说明战术结构已经变了。
32. **`pnpm stall` 报出来的"僵局"要先分清是"很慢"还是"永远打不完"。** 把回合上限调高重跑一次就知道：seed 280 跑到第 59 回合正常结束（只是慢），seed 245 跑了 1000 回合还在继续（真死循环）。**两者要区别对待，否则会把慢局当 bug 修，也会把真死循环当"运气差"放过去。**
33. **出现新僵局时，先做 A/B 对照确认是自己引入的，再动手。** 我一度以为"增援只是把对局拉长、暴露了本来就有的问题" —— 跑「有增援 / 无增援」两组对照（同种子）才发现无增援那组是 0 局，责任在我。**但也正因如此才追到了真正的根因在战斗公式（伤害下限），而不是在增援。**
34. **"双方伤害都恰好为 0"是一种无法取胜的状态，必须从规则上排除。** 它只在刀刃上（攻防差 1 点就正常），出现概率极低（2000 局 1 局），但一旦出现就是死循环，靠调数值几乎不可能避开。**保证"每次命中至少掉 1 点" + "交战时不回血"，就能从数学上保证任何对局都能收场。**
35. **一个取"当前在看的对象"的辅助函数，绝不能顺手过滤掉"已经行动完"的单位。** 我用 `selectedUnit()`（语义是"还能不能接受指令"）去实现"打完还能换武器"，它对着已行动的单位返回 `null`，然后 `equipWeaponAt` 一声不响地 `return` —— **功能静悄悄地从来没生效过，不报错、不崩溃、测试也全绿。** 后来拆成 `inspectedUnit()`（当前在看谁）和 `selectedUnit()`（还能不能下令）两个方法。**凡是"看起来做了但没做"的功能，先查这种提前 return。**
36. **凡是有上下限的资源，加减顺序就是有语义的。** TP 的"扣消耗 20"和"命中回复 8"，分两处写的自然顺序（先回复、再扣）会让回复先被 `maxTp` 夹住，**凭空少掉几点**：95 − 20 + 8 = 83 正确，`min(100, 95+8) − 20 = 80` 错误。所以两者必须基于同一份战果在同一个函数里结算 —— 和经验值同一个道理。**这种误差很小、不会崩、每局都在发生，只有写成单测才抓得住。**
37. **"资源从 0 开始"会让新机制在短关卡里彻底隐形。** 战技最便宜的要 15 TP，每回合 +5 → 第 4 回合才用得上，而第一关平均只打 6.7 回合。更要命的是**按 Q 没有任何反馈**（当时的实现发现"没有可用的战技"就静默返回），玩家只会认为功能坏了。**给新机制一个开局就能用上的初始值，并且永远不要让它"按键无反应"** —— 哪怕只是弹一句"TP 不足，还差 12 点"。
38. **给双方都发的强化，对"人多的一方"收益更大 —— 因为一个阶段里人多的一方能连续行动。** 开局 30 TP 双方都发，通关率从 44.3% 砸到 31.3%（敌人 5~6 个单位集体齐射，玩家 4~5 个轮流动）；改成只发玩家方回到 43.3%。**凡是"开局资源/一次性增益"这类设计，都要先问一句：双方人数一样吗？**
